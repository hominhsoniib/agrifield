## Quyết định kỹ thuật phát sinh ngoài bản kế hoạch gốc

*(Ghi lại đây bất kỳ giả định/quyết định nào chủ dự án đã duyệt trong lúc code, để phiên sau không hỏi lại hoặc làm khác đi.)*

- **Next.js version:** giữ nguyên Next.js 16.3.5 + React 19 (khác "Next.js 14" ghi trong plan mục 1) — chủ dự án đã xác nhận, không hạ phiên bản.
- **`middleware.ts` → `proxy.ts`:** Next.js 16 deprecate hẳn convention `middleware.ts`, bắt buộc đổi tên thành `proxy.ts` (export function `proxy` thay vì `middleware`). Không phải lựa chọn — yêu cầu bắt buộc của framework, đã áp dụng đúng theo `node_modules/next/dist/docs/.../proxy.md`.
- **Cách seed admin/org:** dùng script Node (`supabase/seed/seed.mjs`, chạy bằng `npm run seed`, đọc env qua `node --env-file=.env.local`) gọi Supabase Admin API (`auth.admin.createUser`) thay vì insert SQL thẳng vào `auth.users` — insert tay vào bảng nội bộ của Supabase Auth (mã hoá mật khẩu...) dễ vỡ, không phải cách khuyến nghị chính thức. Không hardcode secret.
- **RLS cho `profiles` + `organizations`:** plan gốc mục 2 không bật RLS cho 2 bảng này. Chủ dự án cung cấp SQL cụ thể, đã thêm vào migration 0001: `profiles` — ai đăng nhập cũng SELECT được (cần cho UI hiện tên), user chỉ UPDATE được chính mình và KHÔNG tự đổi được `role`/`organization_id` (đã kiểm chứng thực tế — xem Nhật ký), admin UPDATE được tất cả; `organizations` — SELECT cho user đã đăng nhập, INSERT/UPDATE chỉ admin.
- **Cấu trúc thư mục:** dự án nằm thẳng ở gốc `D:\AgriField`, không có subfolder `farmtrack/` như plan mục 3 mô tả — do chủ dự án tự chuyển file lên gốc.
- **Mức độ RLS cho `storage.objects` (bucket `attachments`) — CHẤP NHẬN CÓ CHỦ ĐÍCH, cần rà lại ở Sprint 5:** chủ dự án được hỏi rõ trade-off giữa (a) đơn giản — chỉ `auth.uid() is not null` — và (b) siết chặt — join `storage_path` ngược về `farm_id` qua `has_farm_access()`. **Chủ dự án chọn (a).** Migration `0003_storage_attachments_policy.sql` giữ nguyên như bản đã viết.
  - **Hệ quả chấp nhận:** mọi user đã đăng nhập đọc/upload được BẤT KỲ file nào trong bucket `attachments` nếu biết đúng `storage_path` — không giới hạn theo farm_id.
  - **Lý do chấp nhận (chủ dự án nêu):** `storage_path` chứa UUID không đoán được (không lộ qua UI bình thường, chỉ lộ nếu có ai đó chủ động dò/khai thác); ảnh nhật ký nông trại không nhạy cảm bằng dữ liệu tài chính/định danh; join chặt theo farm_id qua `entity_type` polymorphic (3 bảng khác nhau tuỳ loại entity) phức tạp hơn đáng kể so với lợi ích ở giai đoạn MVP.
  - **⚠️ ĐÁNH DẤU RÀ LẠI Ở SPRINT 5** (mục 4.5 việc 1 — "rà soát toàn bộ phân quyền theo role"): nếu dự án lên production thật với dữ liệu nhạy cảm hơn (không chỉ ảnh nông trại), cần quay lại xem xét siết chặt policy này (phương án (b) đã có sẵn, chỉ cần chủ dự án duyệt lại).
- **Cách áp migration lên DB thật:** chủ dự án tự dán nội dung file migration vào Supabase Dashboard → SQL Editor → Run (không đưa Postgres connection string hay access token cho Claude Code). Claude Code KHÔNG có quyền chạy DDL trực tiếp lên DB. Quy trình cho mọi migration tương lai: Claude Code viết file `supabase/migrations/000N_*.sql` → chủ dự án tự chạy trên Dashboard → báo lại → Claude Code verify bằng service role key (SELECT/RPC qua Data API).
- **Bucket Storage `attachments`:** tạo ở chế độ **private** (`public: false`) — ảnh nhật ký truy cập qua app đã auth (signed URL), không public trực tiếp. Không có trong plan, quyết định theo nguyên tắc bảo mật mặc định vì dữ liệu farm đã được kiểm soát bằng RLS.
- **`SUPABASE_SERVICE_ROLE_KEY` / anon key format mới:** project Supabase này dùng format API key mới — anon key dạng `sb_publishable_...`, service role key dạng `sb_secret_...` (thay cho JWT `anon`/`service_role` cũ). Tương thích bình thường với `@supabase/ssr` và `@supabase/supabase-js`, không cần đổi code.
- **`.env.local` bị lỗi BOM:** file gốc chủ dự án lưu có byte-order-mark ở đầu, khiến `node --env-file` đọc sai biến đầu tiên. Đã strip BOM (không đổi giá trị).
- **Supabase CLI login không chạy được trong phiên Claude Code:** `npx supabase login` cần luồng OAuth qua trình duyệt; môi trường thực thi của Claude Code không có TTY (`LegacyLoginMissingTokenError: Cannot use automatic login flow inside non-TTY environments`) nên không tự đăng nhập được, kể cả chạy nền. Chủ dự án đã tự chạy `supabase login` + `supabase gen types` trên PowerShell máy cá nhân (ngoài phiên Claude Code) rồi đưa kết quả vào. Quy trình cho lần sau: các lệnh cần OAuth/trình duyệt tương tự phải do chủ dự án tự chạy ngoài phiên.
- **File `types/database.types.ts` bị lỗi encoding UTF-16:** PowerShell mặc định `>` redirect ra UTF-16LE (kèm BOM `FF FE`), không phải UTF-8, khiến file bị chèn null-byte giữa mỗi ký tự khi đọc như text thường. Đã tự động phát hiện và convert lại UTF-8. Lưu ý này cho mọi lệnh tương lai chủ dự án chạy trên PowerShell rồi redirect `>` vào file trong repo — nên dùng `| Out-File -Encoding utf8` thay vì `>` trần để tránh lặp lại lỗi.
- **shadcn/ui dùng `@base-ui/react` thay vì Radix UI:** khi chạy `npx shadcn@latest init -d` ở Sprint 2, CLI shadcn phiên bản hiện tại (preset mặc định `base-nova`) tự sinh component (`button`, `input`, `select`, `dialog`, `table`, `card`, `badge`, `textarea`, ...) dựa trên thư viện primitive `@base-ui/react` thay vì Radix UI như các bản shadcn cũ/phổ biến trong tài liệu có sẵn. Đây KHÔNG phải lựa chọn chủ động của Claude Code — là hành vi mặc định của CLI tại thời điểm chạy, plan gốc không chỉ định thư viện primitive cụ thể (chỉ ghi "shadcn/ui"). Hệ quả cần biết: API một số component hơi khác Radix quen thuộc (vd: `DialogTrigger`/`DialogClose` dùng prop `render={<Button/>}` để polymorphic thay vì Radix's `asChild`; `Select` dùng `onValueChange` nhận `string | null`). Không ảnh hưởng chức năng, chỉ ảnh hưởng cách viết code khi thêm component mới — nếu tra cứu tài liệu/ví dụ shadcn+Radix ở ngoài, cần đối chiếu lại API thật trong `components/ui/*.tsx` của chính repo này trước khi áp dụng.
